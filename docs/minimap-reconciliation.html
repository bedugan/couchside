Use turn-ins to calibrate sampled positions

A known, isolated turn-in provides an independent reference. Its structured quest position predicts where the icon should appear. We can compare that with the tooltip region found by a stationary scan.

  1. Choose a ready turn-in whose “?” is inside the minimap, away from the rim and other pins. Avoid using the focused navigation arrow as the target.
  2. Compare the existing quest model's predicted location, bearing and distance with the scan's raw hit region. The scanner already saves raw hits even when quest filtering removes them from the gathering display.
  3. Repeat at another zoom, while facing another direction, and with a rotating minimap. Record disagreement instead of adjusting the result to look right.
  4. If the conversions agree, test reversing them: estimate a sampled herb's world position, then predict its minimap position after walking. Compare with a fresh scan and ordinary hover.

This could let herb arrows follow movement between scans. It remains an inference. Pin hitbox centers are approximate, edge arrows can be clamped, and a herb can disappear while a cached position remains. Moving sweeps still need their own validation.

The scale reference is C_Minimap.GetViewRadius(), declared in yards. Couchside's turn-in model already uses it to project world positions onto the minimap.

Category toggles would let someone show resources alone or include ready turn-ins and available quests. Unidentified tooltip text would stay under other tracking. Accepted quest objectives and blue quest areas already have their own display, so including them would be a separate choice.

Today a teal quest A and a gold scan A can represent different locations. A combined display must keep the legend, pin badges and tracker tags consistent. The latest proposal uses separate marker families for herbs and quests.

Latest direction: permanent herb symbols, stable quest letters or numbers.
Every observed Mageroyal location shares the purple diamond, with that meaning retained across rescans, zones and reloads. Specific quests keep labels tied to their quest IDs. Separate marker families would remove the need for a shared herb/quest symbol allocator.

The legend only needs symbols and names; Brian considers the native player arrow and minimap orientation sufficient for direction. Per-location arrows and follow controls are unnecessary for this concept. Shape, color, a contrasting outline and adjustable size make the markers easier to distinguish without requiring color alone.

The current quest display renumbers by distance. The node candidate keeps letters fixed within one snapshot, clears during motion, and assigns them anew by screen position on the next scan. Both rules need revisiting before automatic refresh or a combined display. The symbol decision removes the need for individual herb identity just to keep its type's symbol stable. Moving-pin placement still needs calibration. Multiple specific quests at one giver need a readable grouping treatment.

The earlier encounter-based pool could change meanings in a later encounter. Permanent herb meanings require a fixed catalog instead. The eight familiar raid symbols are too few for the full Classic herb range. Custom textures or shape/color combinations can expand the set, but we need a complete current-client herb catalog and a review at actual minimap size before claiming every symbol is distinguishable.

The latest prototype comparison uses an illustrative eight-herb catalog and stable quest numbers. A ninth herb stays unmarked rather than borrowing another herb's symbol. It demonstrates the required assignment behavior, not full game coverage. Our lookup only governs Couchside's marks; it cannot reserve symbols used by Blizzard or other addons.

Give the minimap view its own module

Brian found a roadside merchant that the classifier did not label as a herb, followed by Mageroyal that it did recognize. That name is still useful to a controller user. Recognizing a category should add meaning to an observation, rather than decide whether the observation deserves to appear.

For example, a Mageroyal name match can get the permanent purple diamond once the symbol display is validated. A merchant name without reliable role metadata stays named tracking. We should not infer a merchant icon from its name alone. The later town scans contain NPC names, but do not establish which observation Brian meant by the roadside merchant or capture the classifier report output.

The broader view must preserve quest observations before applying category rules. Gathering currently excludes known quest titles and objectives; that policy belongs to a resources-only view. Navigation arrows and quest areas need context treatment, because their sampled regions are not ordinary node locations. Structured quests and sampled names should only be joined when the evidence supports that identity.

The next implementation step would extract the existing scanner and snapshot lifecycle with unchanged sampling behavior, preserve old commands and saved history deliberately, then add the optional quest information. Review static models for the broader categories before changing the installed display. No framework or additional dependency is needed for that first step.

This is an ownership proposal. The installed module is still Gathering, with its tested letter-based list. A general minimap view and its migration have not been implemented.

Include names that explain otherwise similar pins

Brian refined the scope after scanning in town. Innkeepers, repairs, transportation and other recognizable service icons should keep their native presentation. Tracked humanoids, beasts and other creatures belong in the nearby view because similar dots can represent different creatures.

Verify available quests before adding them

C_QuestLine.GetAvailableQuestLines(playerMapID) is the first candidate, alongside native forced-visible offers. The generated quest-line declarations include quest ID, name, coordinates, hidden/in-progress state and starting map. That does not establish exhaustive Classic/Forever coverage.

The next diagnostic should compare those APIs with visible ordinary yellow “!” pins while no NPC dialogue is open. It should also report GetQuestsOnMap(playerMapID) with start-marker fields. Missing APIs, empty results and unavailable data must remain distinct. An offer on the world map is not proof that a corresponding minimap pin is visible; nearby range, floors, tracking filters and actual eligibility need checking.

A stricter turn-in classification should also require an accepted quest, a ready/completed state and a non-start marker. The current nearby model only tests completion. Blizzard's offer provider creates start markers, so available offers and hand-ins need separate classification. This is a source-based concern, not a reproduced bug.

A simple classifier and dependency choice

A diagnostic candidate is now installed for a read-only check of saved text: /cs gathering classify [scanID]. Its seed catalog contains the five English herb names independently observed in Brian's tests. It reports resource name candidates, quest text, unknowns and ambiguous matches, including resource/quest names excluded by the existing filter. It leaves the live list and native state unchanged.
