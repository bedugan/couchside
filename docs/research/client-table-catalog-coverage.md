# Client-table catalog coverage

Source check for the read-only export experiment against Forever build `1.60.1.70338`. This does not inspect exported rows or establish in-game coverage.

## Finding

The pinned [wow.export revision](https://github.com/Kruithne/wow.export/tree/c2fd7bde36a712be78a5da896c995b84fbfa2545) has a [table export view](https://github.com/Kruithne/wow.export/blob/c2fd7bde36a712be78a5da896c995b84fbfa2545/src/js/modules/tab_data.js), a [legacy DBC reader](https://github.com/Kruithne/wow.export/blob/c2fd7bde36a712be78a5da896c995b84fbfa2545/src/js/db/DBCReader.js), and a [DB2 reader path](https://github.com/Kruithne/wow.export/blob/c2fd7bde36a712be78a5da896c995b84fbfa2545/src/js/casc/db2.js). This makes a bounded export plausible, but does not make the tables a complete server spawn catalog. The build-specific [WoWDBDefs `GameObjects.dbd`](https://github.com/wowdev/WoWDBDefs/blob/d6f50d4f351193e84226aa62a36faa0f58528afa/definitions/GameObjects.dbd) and [`Creature.dbd`](https://github.com/wowdev/WoWDBDefs/blob/d6f50d4f351193e84226aa62a36faa0f58528afa/definitions/Creature.dbd) both list build `1.60.1.70338`, so these are justified small tables to inspect.

`GameObjects` contains localized name, ID, display ID, map relation, position, rotation, flags, scale, `TypeID`, phase fields and properties. The position fields make it a useful candidate for client-known placed objects, but the schema does not say it contains every live herb or ore spawn, nor does it include spawn timers or harvest state. `TypeID` is a generic numeric object type; there is no herb-versus-ore field in the definition. Treat it as exploratory evidence only until named rows and their values are checked against observed nodes.

`Creature` contains localized names and titles, classification, creature type/family, display IDs and always-equipped items. It has no spawn coordinates, NPC service flags or quest-role field. It can help resolve client-known creature names and appearances, but cannot alone classify trainers, vendors, quest givers or every server-spawned NPC.

This limitation matches the general client/server split documented by AzerothCore: its [world data model](https://github.com/azerothcore/wiki/blob/master/docs/gameobject.md) separates a gameobject template from individual spawned gameobjects, and its [client-cache notes](https://github.com/azerothcore/wiki/blob/master/docs/client-cache-wdb.md) describe creature/gameobject query responses being cached locally. That is corroborating emulator documentation, not proof of Forever's server internals. Such caches are partial query history, not a complete catalog or proof an object is currently spawned.

Related display tables such as `GameObjectDisplayInfo`, `CreatureDisplayInfo` and `CreatureModelData` can explain assets referenced by the two tables. Their schemas concern display/model data, so they are not an alternative source of resource categories or NPC roles. `GameObjects.TypeID` may help group broad object kinds, but the current source check does not establish a reliable ore/herb split from it.

## WDB cache follow-up

The on-disk cache is a candidate for inspecting gathered-object templates, but its coverage is historical and partial. [wowdev's WDB format page](https://wowdev.wiki/WDB) documents the reversed `WGOB` signature for `gameobjectcache.wdb`; for WDB versions from 1.6 it lists a 20-byte header with signature at `0x00`, client version at `0x04`, locale at `0x08`, internal record size at `0x0C`, and record version at `0x10`. The page only verifies that header rule through client 1.9.4. Do not assume that these offsets fully describe Forever's `1.60.1.70338` file: first confirm its magic and header values. The documented record-size field describes the in-memory record, not its serialized file length.

The maintained [ClassicAPI parser](https://github.com/brues-code/ClassicAPI) targets WoW 1.12.1, so it is corroboration for the vanilla-era cache contract, not proof of Forever's exact disk layout. It identifies the gameobject cache key as the server gameobject template/entry ID and exposes cached type, display ID and name. Its [cache field offsets](https://github.com/brues-code/ClassicAPI/blob/master/src/Offsets.h) are offsets in the client's loaded in-memory record, not raw-file offsets. The vanilla [`SMSG_GAMEOBJECT_QUERY_RESPONSE` message definition](https://docs.rs/wow_world_messages/latest/i686-unknown-linux-gnu/wow_world_messages/vanilla/struct.SMSG_GAMEOBJECT_QUERY_RESPONSE.html) has a separate entry ID followed by type, display ID, names and raw data. No checked source establishes a numeric-key join between that server entry ID and `GameObjects.db2.ID`; do not join on numeric equality alone.

There is a plausible indirect herb/mining discriminator in the cache payload: for the classic chest gameobject type, raw data begins with the lock ID (`data0`). The [classic gameobject-template reference](https://github.com/TrinityCore/tc-wiki/blob/main/database/335/world/gameobject_template.md) documents that chest type 3's `data0` is the `Lock.dbc` lock ID. The build-matched [`Lock.dbd`](https://github.com/wowdev/WoWDBDefs/blob/d6f50d4f351193e84226aa62a36faa0f58528afa/definitions/Lock.dbd) defines lock slots where `Type = 2` means a skill requirement and `Index` refers to `LockType::ID`; the same build has [`LockType.dbd`](https://github.com/wowdev/WoWDBDefs/blob/d6f50d4f351193e84226aa62a36faa0f58528afa/definitions/LockType.dbd). Classic lock type IDs 2 and 3 are Herbalism and Mining respectively ([server enum reference](https://github.com/azerothcore/azerothcore-wotlk/blob/master/src/server/shared/SharedDefines.h)). This is a candidate crosswalk, not yet verified against Forever's cache payloads or its actual lock rows. A cache type of chest alone is too broad; verify that the payload's first lock ID resolves through the build-matched Lock and LockType tables before using it.

A WDB cache records templates whose query responses the client has received; it does not report live spawn state or prove complete catalog coverage. The [client-cache reference](https://github.com/azerothcore/wiki/blob/master/docs/client-cache-wdb.md) explicitly describes creature and gameobject query responses being cached. Cache IDs identify template entries in the vanilla parser; `GameObjects.db2.ID` is the primary key of a separate client table with map and position fields. A matching integer does not establish identity across those tables.

For Brian's narrow read, first confirm the WDB header without treating it as parsed. Then inspect only representative cached resource entries and compare their entry ID, broad type, `data0` lock ID and matching Lock/LockType rows. Accept the indirect classification only if known herb and ore examples resolve consistently and unrelated chest objects do not. Keep absent entries unknown: cache membership means “queried at some point,” and cache absence means neither “not a real object” nor “not a live spawn.”

## Minimal acceptance checks for the export

1. Export only `GameObjects`, `Creature`, and, if useful for joins, the display tables. Record the exact client build, exported headers, row counts, and the actual table definition/layout revision used; the app commit does not pin downloaded definitions.
2. Search rows for a small known set of gathering names (for example Peacebloom, Earthroot, Copper Vein and Tin Vein) and several observed NPCs. Record misses, duplicate/localized names, IDs, and all candidate category fields. A schema hit without matching rows is not catalog evidence.
3. Compare `TypeID` values for name-matched herbs, ore and unrelated objects. If herbs and ore share a broad type, or the export lacks known names, leave category resolution to another verified signal and keep unknown/ambiguous observations intact.
4. Do not describe this export as complete spawn coverage. A complete or live catalog would require separate evidence about the server's templates/spawn records; client tables and caches cannot establish that coverage.
