Couchside Gathering 0.11.6 assessment · updated with the 0.12.0 consolidation candidate

Keep two sources of evidence behind one motion guard

The dungeon fallback is useful because the coordinate method cannot support the observed Wailing Caverns case. It provides weaker evidence about actual displacement, so replacing the stronger method everywhere would lose information. The recommended simplification is one owner for motion validation, with the choice of evidence kept inside that module. Version 0.12.0 implements this consolidation locally. Native acceptance of that candidate remains pending.

What accuracy means here

Both guards use the same tooltip scanner, approximate regions and minimap placements. They do not calculate herb locations differently. They decide whether a scan can be shown and whether its locations should be cleared as stale.

Runtime cost

The display checks at 10Hz only while visible, for at most ten seconds. During a scan, both paths also sample before query batches. Before 0.12.0, the dungeon path retried the unavailable coordinate/facing reads, created error results and then performed five additional native reads: instance state, rotation mode, speed, movement status and instance ID.

That is about 50 extra native reads per second during visible checking, plus the primary attempts and Lua work. It is an operation count, not a CPU measurement. No native timing comparison establishes a frame-time or memory advantage for either guard.

Nine movement/transition event listeners remain registered whenever nearby tracking is enabled, including outdoors and while the list is absent. Their handlers only increment a revision and retain the event name; they do not poll or query positions. Disabling nearby tracking releases them. The typical 1,009-point scanner is shared by both approaches, so changing the motion guard does not eliminate that scanning work.

Maintenance is the clearer concern

Before consolidation, selection, scan classification and live comparison spanned ScanMotion.lua, DungeonMotion.lua and NearbyList.lua. The display knows which method was chosen and how to compare each one. That spread motion knowledge across callers and made it easier for scan acceptance and later clearing to diverge. In 0.12.0, MotionGuard owns both comparisons and NearbyList uses its verdict.

MotionGuard now owns capture, acceptance and later validity. The scanner and display use the same small interface. It prefers readable coordinates/facing, uses the tested dungeon evidence when supported, and retains the chosen source and limitations in diagnostics. The common expiry, combat, geometry and option policies remain shared. No dependency or general provider framework is needed.

Once a snapshot chooses the dungeon mode, its live checks read that mode directly rather than repeatedly trying known-unavailable coordinate reads. A new scan or context transition would reassess capabilities. Version 0.12.0 implements that selected-mode check. Twenty fixture checks made zero extra map/facing calls, but no game-client timing comparison has been measured.
